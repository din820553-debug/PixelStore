# Хранение покупок и документов

## Что готово

- Node.js 24 + встроенная SQLite, без внешних npm-зависимостей.
- Серверное сохранение заказа и состава с ценами на момент оформления.
- Отдельные статусы оплаты и выполнения; отметки оплаты/возврата только продавцом после ручной сверки. Подключённого платёжного API и автоматического списания нет.
- Витрина на сервере создаёт **демозаказы**, не реальные оплаченные покупки. Кнопка продавца «Внести покупку вручную» предназначена для учёта реально принятых вне сайта заказов и не принимает деньги.
- Приватные PDF/JPEG/PNG/WebP до 5 МБ, до 20 файлов на заказ. Файлы находятся в BLOB-полях SQLite, не в каталоге сайта. SHA-256 идентифицирует загруженную копию, но не доказывает подлинность документа.
- Типы документов: подтверждение поставщика, подтверждение оплаты, выданный фискальный чек, другое. По умолчанию файлы видит только продавец. При загрузке можно явно разрешить скачивание покупателю по секретному ключу его заказа. Доступ можно открыть или закрыть позже; уже скачанные копии это не удалит.
- История действий продавца: отметки оплаты, выполнения, расходов, заметок и загрузки документов. Записи не редактируются через интерфейс.
- Поиск по номеру/нику, фильтры, экспорт CSV, резервная копия всей базы вместе с файлами.
- Фактические расходы: закупка, комиссия карты, приём платежа, вывод, налог/отчисление, другое. Остаток рассчитывается по введённым суммам с учётом отмеченного возврата. Это не автоматический налоговый учёт и не гарантия чистой прибыли.

## Что означает «чек»

Система умеет **хранить уже выданные документы** и скачать описание заказа. Описание заказа явно помечено «Не является фискальным чеком». Фискальные чеки система не выпускает и не отправляет в ФНС. Если по модели продаж нужна фискализация, она подключается через подходящее решение отдельно. Статус/регион/модель продавца нужно определить до запуска реальной оплаты.

## Два режима витрины

1. **GitHub Pages без настроенного VPS:** `api-config.js` содержит пустой адрес. Создаются локальные демозаказы, продавцу ничего не отправляется. История этого браузера содержит снимки всех новых заказов. Информация о локальном режиме показана в корзине и разделе «Мои заказы».
2. **Node-сервер:** автоматически отдаёт конфигурацию того же origin; заказы хранятся в SQLite. Либо GitHub Pages обращается к установленному HTTPS-серверу через явно заданный адрес в `api-config.js`. При недоступном настроенном сервере оформление показывает ошибку; молчаливого переключения на локальное хранение нет.

История покупателя хранит секретные ключи к его заказам на этом устройстве. Скачанное описание содержит номер, идентификатор и ключ. Это позволяет открыть заказ на другом устройстве через «Мои заказы → Открыть заказ с другого устройства». Не публикуйте эти ключи. Продавец не получает список чужих заказов через публичный API. Старые демозаказы из прежнего `pixel-last-demo-order` автоматически не импортируются: в них не было надёжных снимков всех цен и серверного идентификатора. Старый ключ не удаляется; ранее скачанные файлы остаются у пользователя.

## Локальный запуск

Нужен Node.js 24 или новее с модулем `node:sqlite`.

```sh
node --check app.js
npm test
```

Задайте случайный `ADMIN_TOKEN` длиной минимум 32 символа через окружение. Для генерации на своём сервере можно выполнить:

```sh
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Не присылайте ключ в чат, не вставляйте в клиентский JavaScript и не коммитьте. Затем `npm start`, витрина http://localhost:3000, кабинет http://localhost:3000/admin. Без ADMIN_TOKEN сервер сохраняет демозаказы, но вход в кабинет отключён. При перезапуске сервер завершает старые сеансы продавца; потребуется войти снова.

## Установка на VPS h1cloud

Нужны SSH-доступ, домен/поддомен с DNS на VPS, Node.js 24+, HTTPS и постоянный диск. Реальные реквизиты VPS, доступ SSH и домен пока не внесены в проект. Ниже шаблон, не результат установки.

1. Убедитесь, что выбранная модель продаж согласована, и сделайте резервную копию существующего сайта. Не заменяйте работающий конфиг Nginx целиком.
2. Разместите код из GitHub в `/opt/pixelstore`. Для обновления используйте штатный Git-доступ или архив без runtime-данных. `npm install` не требуется: внешних зависимостей нет.
3. Создайте системного пользователя `pixelstore` без административных прав. Создайте `/var/lib/pixelstore`, владелец — этот пользователь, режим `0700`. База и файлы будут только там, а не в публичном каталоге веб-хостинга.
4. Создайте `/etc/pixelstore.env` с правами `0600` и заполните:

```text
HOST=127.0.0.1
PORT=3000
DATA_DIR=/var/lib/pixelstore
ADMIN_TOKEN=<случайный секрет, созданный на VPS>
PUBLIC_ORIGIN=https://orders.example.com
ALLOWED_ORIGINS=https://din820553-debug.github.io
```

`PUBLIC_ORIGIN` — точный HTTPS-origin сервера, без пути. `ALLOWED_ORIGINS` — origin витрины, без `/PixelStore/`; несколько адресов перечисляются через запятую. Нельзя ставить `*`. Если витрина переедет на собственный домен, добавьте его origin.

5. Скопируйте `deploy/pixelstore.service.example` в systemd, исправьте путь к Node по результату `command -v node`. Пример использует пользователя pixelstore и каталог `/opt/pixelstore`; они должны существовать. Запустите сервис и проверьте `/api/health` через loopback.
6. Создайте отдельный виртуальный хост по `deploy/nginx.conf.example`, подставьте настоящий домен. Проверьте конфиг Nginx и включите HTTPS через панель/сертификат. Не открывайте порт 3000 наружу: доступ идёт через HTTPS-прокси.
7. Зайдите на `https://orders.example.com/admin`, установите серверную cookie через вход, создайте тестовый заказ и загрузите тестовый документ. Проверьте скачивание с нужным доступом, резервную копию и восстановление. Кабинет должен открываться на origin VPS, а не GitHub Pages.
8. В публичном `api-config.js` установите только адрес сервера:

```js
window.PIXELSTORE_API_BASE = 'https://orders.example.com';
```

Никаких секретов здесь нет. Опубликуйте этот файл на GitHub Pages. Создайте заказ на витрине и проверьте его наличие у продавца. Сначала используется деморежим — реальная оплата остаётся отключённой.

## Резервирование и восстановление

- `DATA_DIR=/var/lib/pixelstore npm run backup` создаёт согласованную SQLite-копию, включая документы. Каталог назначения можно задать `BACKUP_DIR`.
- Кнопка «Резервная копия базы» доступна только вошедшему продавцу, скачивает копию и удаляет временный файл с сервера. Полученный файл содержит персональные данные и документы — храните его закрыто и используйте шифрование диска/хранилища.
- Предлагаемая политика для старта: ежедневная резервная копия, ещё одна перед обновлениями; несколько версий на отдельном защищённом носителе. Это рекомендация, не уже включённое расписание.
- Восстановление: остановить единственный процесс сервера; сохранить текущие файлы базы отдельно; скопировать проверенную резервную копию как `DATA_DIR/pixelstore.sqlite`; убрать только старые `pixelstore.sqlite-wal`/`pixelstore.sqlite-shm` после остановки и сохранения исходной базы; установить владельца/режим `0600`; запустить сервер и проверить заказы и документы.
- Не копируйте только активный `.sqlite` без WAL и не удаляйте WAL работающего процесса. Используйте кнопку или `npm run backup`.
- Не запускайте несколько процессов Node/кластер с разными каталогами базы. Первая версия рассчитана на один процесс и локальный постоянный диск.

## Доступ и ограничения

- Сеанс продавца: HttpOnly, SameSite=Strict, Secure на HTTPS, срок 12 часов. Ключ владельца сравнивается на сервере, не сохраняется в браузерном localStorage; есть ограничение попыток входа.
- Клиентские заказы закрыты 256-битным ключом, который передаётся в заголовке Authorization, а не URL. Сервер хранит хеш ключа. Внутренние заметки и расходы покупателю не возвращаются.
- Продавец вручную проверяет оплату и вводит подтверждение операции. Описание/скриншот сами по себе не являются банковской проверкой. В интерфейсе нет автоматической выдачи и автоматического возврата.
- Цены проверяет сервер по единому `catalog.js`. Старая клиентская цена отклоняется до создания нового заказа. Заказ получает снимок цены; изменение каталога не меняет старые документы. Повтор идентичного запроса возвращает тот же заказ даже после обновления цен.
- Для документов проверяются тип содержимого и размер, скачивание идёт вложением. Антивирусной проверки нет: обрабатывайте только ожидаемые документы из доверенных источников.
- CSV выгружает все найденные сервером заказы, UI показывает до 300 строк с предложением уточнить поиск. Документы целиком входят в SQLite-резервную копию, а не CSV.
- HTTPS, мониторинг свободного диска, ограничение доступа к резервам, сроки хранения/удаления данных и документальная политика продавца настраиваются владельцем хостинга. Автоматическое удаление не включено, чтобы не потерять документы без согласованного срока хранения.

## Что добавить следующим

1. После одобрения кассы — серверная проверка уведомлений провайдера, сверка суммы/валюты/order ID, защита от повторов. Ручные отметки не заменяют эту интеграцию.
2. После выбора налогового оформления — нужный способ выпуска фискальных чеков и их связь с платежом/возвратом.
3. После установки — расписание резервирования и уведомление об ошибках сервера/нехватке диска.

До этого не нужны сложная CRM, аккаунты всех покупателей или рекламная аналитика. Основной приоритет — не терять заказы и доказательства исполнения.
